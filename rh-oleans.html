Compiled oleans for the alpo.ge Proof of the Riemann Hypothesis

Explore the dependency graph of the proof → Look up any of the 806,982 declarations the final theorem uses and see what it uses and what uses it.

The mathematics and its Lean formalization are the work of Levent Alpöge, working with Claude. His note announcing it is alpo.ge/remark.pdf, and the Lean source is the fourteen parts alpo.ge/lean.tar.gz.part01 … part14. This page only hosts files built from that source.

The .olean file of every one of the 175,187 modules in the Lean development posted at alpo.ge/lean.tar.gz.part01 … part14, which states a proof of the Riemann Hypothesis, together with the Mathlib .oleans it was compiled against. They are here so that independent kernels and checkers can be run on it without first spending about 530 CPU-hours compiling.

Made possible by the support of Grant 63750, “Explaining Universal Truths”, from the John Templeton Foundation, Project Lead Simon DeDeo. Additional support from research funds of the Laboratory for Social Minds and from the Survival and Flourishing Fund.

These are build products of someone else’s code, which we have not reviewed. Sharing them is not a statement about whether the proof is correct. Two lean4export files made from them are further down; no second kernel has been run on any of it here.

Checks run on this build

Two checks have been run here, both with Lean v4.33.1 itself. Neither involves a second kernel; the files below are there so that others can do that.

Axioms

The output of #print axioms for the five theorems stated in Main.lean:

'riemannHypothesis' depends on axioms: [propext, Classical.choice, Quot.sound]
'riemannZeta_eq_zero_re' depends on axioms: [propext, Classical.choice, Quot.sound]
'LFunction_ne_zero_of_half_lt_re' depends on axioms: [propext, Classical.choice, Quot.sound]
'LFunction_eq_zero_re' depends on axioms: [propext, Classical.choice, Quot.sound]
'LFunction_eq_zero_re_of_isPrimitive' depends on axioms: [propext, Classical.choice, Quot.sound]

Each of the five is a theorem whose type is exactly the named statement: RiemannHypothesis as defined in Mathlib.NumberTheory.LSeries.RiemannZeta for the first, and the four definitions in Statements for the others. #print axioms reports what the compiled environment records. On its own it would not notice a declaration that had been written into an .olean without passing the kernel; the replay is the check for that.

Kernel replay

Every constant of every project module is added again through the Lean kernel, on top of that module’s imports, one module per process. This is the logic of leanchecker’s replayFromImports. As a control, a forged theorem : False compiled with kernel checking switched off is rejected by it. The replay covers the 175,187 project modules, not Mathlib’s own.

    Layout

    alp-oleans/lib/<Module/Path>.oleanThe project’s modules. The entry points are lib/Main.olean and lib/Statements.olean.
    alp-oleans/deps/<package>/…The full build/lib/lean of mathlib, batteries, aesop, Qq, proofwidgets, importGraph, plausible and LeanSearchClient.

    LEAN_PATH, in the order used for the build, where R is the alp-oleans directory and T is the v4.33.1 toolchain:

    R/deps/batteries:R/deps/Qq:R/deps/aesop:R/deps/proofwidgets:R/deps/importGraph:
R/deps/LeanSearchClient:R/deps/plausible:R/deps/mathlib:R/lib:T/lib/lean

    The project files are plain .oleans that do not use the module system; Mathlib’s are module-system ones (.olean, .olean.server, .olean.private). All of them are specific to Lean v4.33.1.

    How they were built

    Source. The fourteen parts concatenated, SHA-256 9631b4f020199e580ba86178cb56c6e9b09f690c2369a80dc4334aa93f49c7fc, with the toolchain and dependencies pinned by its own lean-toolchain and lake-manifest.json.

    Not with lake build. Lake does not scale to this tree: for each module it re-walks about 8,800 transitive imports and writes a setup file of about 6 MB. Each module was instead compiled by the pinned lean binary directly, one process per module, in dependency order:

    lean --tstack=400000 src/<Module/Path>.lean -o lib/<Module/Path>.olean --setup <json>

    with LEAN_PATH as above and this setup file:

    {"name": "<Module.Name>", "package": "tree", "isModule": false,
 "options": {"autoImplicit": false, "relaxedAutoImplicit": false, "maxSynthPendingDepth": 3,
             "pp.unicode.fun": true, "maxHeartbeats": 4000000},
 "importArts": {}, "dynlibs": [], "plugins": []}

    Those are the lakefile’s options; modules under GroundTheory.LocalFields and GroundTheory.GlobalFields also get "synthInstance.maxHeartbeats": 400000, as the lakefile specifies. This is the command line, module name, package name and options that Lake itself passes, without the import table and without the -c and -i outputs. So there are no .ilean, .c or .ir files and no Lake .trace or .hash files, and Lake will not regard these as an up-to-date build.

    Dependencies were not rebuilt. The dependency .oleans are the ones lake exe cache get downloads for that Mathlib commit, from Mathlib’s official build cache.

    Result. All 175,187 modules compiled with no errors. One compiler process segfaulted inside the bundled allocator and the module succeeded on retry; 64 further recompiles of that module all gave a byte-identical .olean, identical to the one included here.

    What to check

    Main.lean, in the source tarball, states five theorems. riemannHypothesis : RiemannHypothesis uses Mathlib’s own definition. The other four, riemannZeta_eq_zero_re, LFunction_ne_zero_of_half_lt_re, LFunction_eq_zero_re and LFunction_eq_zero_re_of_isPrimitive, use the definitions in Statements.lean, which imports only Mathlib.
